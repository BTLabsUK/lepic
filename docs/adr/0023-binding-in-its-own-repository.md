# 0023 The Flutter binding lives in its own repository

Status: accepted
Date: 2026-10-23

## Context

Until now the Dart package (generated by flutter_rust_bridge 2.13 from `crates/lepic-ffi/src/api`),
its build hook, its tests and the device test app lived in `bindings/flutter/`, and
`cargo xtask mobile` ran `flutter` for the host and device tests. The operator decided on
2026-10-23 that LEPIC holds no Flutter or Dart: it is a Rust library with a Rust FFI API, and the
binding is a separate project that pins a LEPIC commit.

flutter_rust_bridge generates two halves from one parse of the API: `frb_generated.rs`, compiled
into `lepic-ffi`, and the Dart files. Both embed a hash of the API they were generated from, and
the Dart side refuses to start against a library whose hash differs. The code generator needs a
Dart toolchain even to write the Rust half. The API imports `StreamSink` from `frb_generated`, so
the Rust half cannot leave the crate without changing the API.

## Decision

- The binding moves to its own repository, gitlab.com/epic-cash-bt/lepic-flutter, as the Dart
  package `lepic`, version 0.1.0. It pins a LEPIC commit in `lepic.rev` and holds the codegen
  configuration, the generated Dart, the build hook, the tests, the device test app and
  `tool/lepic.sh`, which builds the native libraries from the pinned LEPIC per platform. Apps
  depend on that package.
- `frb_generated.rs` stays in `crates/lepic-ffi`. It is written only by the binding's
  `tool/lepic.sh generate`, in the same run as the Dart half, against a LEPIC checkout, and
  committed to LEPIC.
- That run also writes `crates/lepic-ffi/bridge.sha256`: the SHA-256 of every file under
  `src/api` and of `src/frb_generated.rs`. `cargo xtask repo-lint` (part of `cargo xtask check`)
  fails when any of them differs from the record, when a file is added or removed, or when
  `frb_generated.rs` comes from another flutter_rust_bridge version than `Cargo.lock` resolves. So
  LEPIC cannot change the API, or the Rust half, without both halves being generated again.
- The binding's `tool/lepic.sh check` generates both halves again at its pin and fails unless
  the Dart files equal the committed ones and `frb_generated.rs` and `bridge.sha256` equal the
  pinned LEPIC's. So the binding cannot pin a LEPIC whose Rust half does not match its Dart half.
- `cargo xtask mobile --package` writes the libraries and their `SHA256SUMS` to `--out <dir>`,
  by default `dist/native/`; `--mock` builds them with the scripted node and relay for the
  binding's tests, by default into `dist/native-mock/`. xtask runs no Flutter or Dart.

## Consequences

- Changing the API is a two-repository change: edit `src/api` on a LEPIC branch, run the
  binding's `tool/lepic.sh generate` against that checkout, commit `frb_generated.rs` and
  `bridge.sha256` in LEPIC and the Dart in the binding, then move the binding's pin.
- LEPIC's checks need no Dart toolchain; the binding's checks need Flutter and a Rust toolchain.
- The Dart host and device tests run from the binding repository, against the library built from
  its pinned LEPIC.
- This supersedes the delivery bullet of ADR 0007 and its consequence that host tests run here.
  The rest of ADR 0007 stands.

## Alternatives considered

- Generate `frb_generated.rs` in the binding repository, in a wrapper crate over `lepic-ffi`: the
  API would have to stop using the generated `StreamSink`, and the halves would then live
  together, but the shipped library would be built outside LEPIC.
- Keep generating in LEPIC with a Dart toolchain in its CI: keeps Dart tooling and configuration
  in LEPIC, which the decision rules out.
- Move the package into the app repository as a local package: ties the binding to one app and
  its release cycle, and the app's developers do not edit LEPIC code.
